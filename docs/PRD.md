# JackDevOps PRD（产品需求文档）

> 功能以 `feature-inventory.md` 的编号（如 F1、A2）引用，本文档回答"为什么做、为谁做、做到什么程度"。

---

## 1. 产品定位

**JackDevOps** 是一个开源的、AI-ready 的全流程 DevOps 平台，覆盖 **需求 → 开发 → 测试 → 发布 → 运维** 完整交付闭环。

- **一句话**：以服务目录为轴心、以全链路事件流为地基、以 AI Agent 为流程参与者的一站式研发交付平台。
- **形态**：开源社区产品（Apache 2.0），私有化部署为主。
- **对标**：Zadig（工作流/发布编排）+ Backstage（服务目录）+ Unleash（特性开关）+ AI Agent（dsh 融合）的融合体。

### 北极星指标

> **新用户从安装到跑通第一条流水线 ≤ 10 分钟。**

配套验收标准（每个核心流程）：

| 流程 | 标准 |
|---|---|
| 建项目/接服务 | 操作路径 ≤ 3 步 |
| 建流水线 | 默认模板可用，不写 YAML 也能完成 |
| 发起环境/发布 | 默认值优先，向导式完成 |
| 查看交付状态 | 角色首页一屏可见 |

每个 Phase 交付前执行"新人 10 分钟测试"作为发布门禁。

## 2. 七大痛点与差异化承诺

本产品的核心叙事：**每个核心功能都必须回答"竞品为什么没做到、我们凭什么做到"**。

### 痛点 1：链路断裂（→ F1 事件溯源 + 变更指纹）

**现状**：需求在 Jira、代码在 Git、构建在 CI、发布在 CD、告警在监控——五个工具五本账，出事后人肉串线索耗时数小时。
**竞品盲区**：DevLake 是事后 ETL 拼数据；Zadig/Devtron 只有平台内事件。没有竞品拥有"需求→PR→构建→制品→发布→告警"的完整原生事件链。
**我们的承诺**：从 Phase 1 起以事件溯源架构把全流程存为不可变事件流，任何制品携带**变更指纹**（traceId），排查时一键展开完整因果链。**这是架构级差异，后补成本极高，是我们的第一护城河。**

### 痛点 2：AI 都是孤岛 AI（→ E5）

**现状**：竞品 AI 是点状的——Copilot 只看代码、AI 评审只看 MR。缺上下文的 AI 结论质量低。
**我们的承诺**：F1 的事件流成为 dsh Agent 的上下文源。AI 诊断发布失败时自动携带"这次变更改了什么、哪些测试跑过、过去 24h 同类变更的结果"。**上下文质量决定 AI 上限。**

### 痛点 3：发布审批形同虚设（→ E4）

**现状**：审批人只看到"请审批发布 v1.2.3"，点同意全凭信任。
**我们的承诺**：审批卡片 = AI 风险摘要（变更范围、影响服务、测试通过率、历史回滚记录）+ 一键拒绝并自动创建任务。审批从仪式变成真门禁。

### 痛点 4：回滚不彻底（→ D5）

**现状**：所有竞品的"回滚"= 回滚部署。特性开关忘关、DB 迁移、缓存/队列残留导致"回滚了还炸"。
**我们的承诺**：发布时登记变更关联物清单，回滚按清单逆向执行；DB 迁移属危险区，仅提示不自动执行。

### 痛点 5：测试跑得又多又慢（→ C4）

**现状**：全量跑 1 小时+，拍脑袋选则漏测。竞品只有测试分片（并行），没有基于变更的智能选择。
**我们的承诺**：基于服务目录依赖图 + 历史事件（改 A 文件时哪些测试挂过）做测试影响分析，反馈环从小时级压到分钟级。

### 痛点 6：新人上手 = 考古（→ A2、E6）

**现状**：知识在老员工脑子里、群聊记录里。Backstage 有目录没流水线，Zadig/Devtron 有流水线没目录深度。
**我们的承诺**：服务目录条目 = 负责人 + 文档 + 流水线 + 环境 + 近期变更 + 当前告警，"目录+执行"合一；再叠加目录问答 Agent。

### 痛点 7：需求与交付脱节（→ A5）

**现状**：release notes 手写，需求到生产的 Lead Time 说不清。
**我们的承诺**：需求是事件链的源头，发布说明自动从"本版本包含的需求+PR+提交"生成，Lead Time 全自动。

## 3. 用户画像与角色化工作台（A3）

| 角色 | 打开平台看到的 | 核心诉求 |
|---|---|---|
| 产品经理 | 需求看板、发布状态、Release Notes | 需求到上线的可追溯 |
| 开发 | 我的 PR、流水线状态、我的环境 | 反馈环快、不被打断 |
| 测试 | 测试计划、质量门禁、失败归因 | 少跑无效测试 |
| 运维 | 环境拓扑、发布编排、告警、DORA | 稳定、可回滚、省心 |

---

## 4. 六角色脑暴结论（摘要）

- **产品经理**：差异化不在"又一个 CI/CD"，而在"需求到运维的闭环自动化 + 每个环节的 AI 决策"。MVP 必须有抓手：需求管理 + 工作流 + CI/CD + 部署。
- **架构师**：模块化单体（NestJS）+ 独立执行器 + 事件溯源。LLM 多模型可插拔。Agent 是工作流一等公民。
- **前端设计专家**：三个标志性交互——可视化 DAG 工作流编辑器（AI 节点与流水线节点同框）、全局 AI 侧边栏、环境拓扑图 + 部署时间线；⌘K 命令面板。
- **测试专家**：AI 最佳落地是测试左移（评审/生成）与失败归因，而非替代测试；PR 级临时环境是刚需。
- **开发专家**：API-first，Git 工作流深度集成，不重复造轮子（Kaniko/Helm/Prometheus）。
- **运维专家**：交付形态是生死线（Helm + Compose 双形态）；渐进式交付必须可一键回滚；安全底线（密钥/RBAC/审计）。

## 6. MVP 范围（Phase 1）

**目标**：跑通"项目 → 服务 → 流水线 → 部署 K8s"最小闭环，同时埋下两大差异化地基（F1 事件流、A2 服务目录）。

**包含**（功能 ID）：A1、A2（轻量）、A3、A4（通知）、B1、B2（规则）、B5、C3、D1、D2、D3、D7、F1、F2（基础 RBAC）、F10、F11

**明确不做**：AI 能力（Phase 2）、特性开关、渐进式交付、多租户。

**验收标准**：
1. 新人 10 分钟测试通过
2. 事件流从第一个需求创建起持续记录，任何构建/部署事件可回溯到需求与 PR
3. Trivy 扫描作为流水线默认步骤不可绕过
4. Helm 与 Docker Compose 均可一键部署本平台

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| dsh 处于 developer preview，有破坏性变更 | 零分叉策略：适配器隔离 + 锁版本 + 契约测试升级门禁（见 architecture.md） |
| 范围蔓延（30 项功能的诱惑） | feature-inventory 是唯一事实源；每阶段启动时重审清单 |
| 事件流设计缺陷难返工 | Phase 1 事件 schema 设计评审作为最高优先级技术评审 |
| DB 迁移回滚安全 | 只提示不自动执行（D5 约束） |
